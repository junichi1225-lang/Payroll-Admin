# RDRA 要求分析

RDRA の考え方で要求分析を対話的に進め、成果を常に HTML でプレビューするスキル。

## 心構え

このスキルの利用者には PdM・企画・ビジネス側が含まれる。成果物は彼らが読み、彼らが意思決定に使う。だからこのスキルでは **要求分析だけに徹し、コード・実装・技術選定・データベース設計といった作り方の話には踏み込まない**。

- 技術の話題が出てきたら、要求の言葉へ翻訳して戻す。たとえば「テーブルをどう持つか」ではなく「どんな情報を、いつ、誰が参照・変更するか」を問う
- エンティティは実装上のテーブルではなく、業務で扱う情報のまとまりとして扱う
- 「どう実現するか（How）」ではなく「何が必要か・なぜ必要か（What / Why）」に集中する

利用者が技術に明るいとは限らない。専門用語は避け、業務の言葉で対話する。

## 成果物

利用先プロジェクトの `rdra/` に出力する。

- `rdra/analysis.md` — 分析内容の正。すべての編集はここに対して行う
- `rdra/index.html` — `analysis.md` から生成するプレビュー。ブラウザで開いて見る

## 基本ループ

対話のたびに、次を繰り返す。これがこのスキルの中心。

1. 対話で要素をひとつ掘り下げ、合意する
2. `rdra/analysis.md` を編集して反映する
3. レンダースクリプトで `rdra/index.html` を再生成する
   ```bash
   node "<このスキルのディレクトリ>/scripts/render.mjs" rdra/analysis.md
   ```
   `<このスキルのディレクトリ>` は、このスキルが読み込まれたときに提示される base directory のパス
4. 初回だけ、プレビューの開き方を案内する
   ```bash
   open rdra/index.html
   ```
   一度開けば、以降はページが 10 秒ごとに自動リロードされ、編集が反映される。2 回目以降は `open` を案内しない

`analysis.md` の編集は差分が小さくなるよう Edit を使う。HTML を手で書くことはしない。生成は必ずスクリプトに任せる。

## 初期化

`rdra/analysis.md` が無ければ、`references/markdown-template.md` の構成を雛形にして作る。雛形の例文はそのまま残さず、対象の要求に合わせて書き換える。最初は章だけ用意し、対話で中身を埋めていってよい。

## 進め方

RDRA の流れに沿って、おおむね次の順で洗い出す。ただし一度に全部やろうとせず、対話で一段ずつ深める。後の段で前の段の見落としに気づいたら戻って直す。

1. **アクター・外部システム** — この対象に関わる人・役割と、連携する外部システムを洗い出す
2. **領域（コンテキスト）** — 業務をまとめる単位を見つける
3. **業務一覧** — 領域ごとに業務を並べ、各業務で発生するイベントと、参照・変更されるエンティティを洗い出す
4. **状態モデル** — 主要なエンティティがたどるライフサイクルを整理する
5. **利用シーン** — バリエーションや条件を含む具体的な使われ方を描く

各要素の定義・聞き取りのコツ・よくある落とし穴は `references/rdra-method.md` を参照する。要素を新しく扱い始めるときに読むとよい。

## 表現ルール

`analysis.md` 内での書き分けを統一する。

- **サマリは表** で一覧性を持たせる
- **具体的な内容はネストした箇条書き** で構造を見せる
- **業務は Mermaid のイベントモデリング図** で、アクター→コマンド→イベント→エンティティの流れを色分けして表す
- **状態モデルは Mermaid の `stateDiagram-v2`** で表す
- **各業務に「シーン」と「変更の詳細」をパラグラフで添える**。シーンは現実のどんな場面で・なぜ起きるか、変更の詳細は図に表れない具体的な変更内容（どのエンティティのどんな情報がどんな値で変わるか、業務ルールや既知の制約）を書く。図は関係を示すが、現実の文脈と具体は言葉でしか残らないため

Mermaid の記法と色分け規約は `references/mermaid-conventions.md` に従う。図を書くときは必ず参照し、全業務で見た目を揃える。

## モード

ユーザーの意図でモードを判断する。明示が無ければ現状を確認して提案する。

- **作成・更新** — 対話で要素を洗い出し、聞き取りながら `analysis.md` を育てる。新規・既存どちらも地続きで扱う。これが主役
- **レビュー** — 抜け漏れと整合性を検査する。観点は `references/rdra-method.md` のレビューチェックリストを使う。たとえばイベントに対応する業務があるか、各エンティティに変更する業務が存在するか、領域に業務が紐づいているかを確認し、見つけた問題を指摘する

## 対話のスタイル

- 質問は一度にひとつ。答えやすいよう選択肢や具体例を添える
- ユーザーの挙げた要求を鵜呑みにせず、抜けている観点や矛盾を率直に指摘する。指摘には根拠を添える
- 専門用語を避け、業務の言葉で話す
- 区切りのよいところで「ここまでで合っていますか」と確認し、合意してから次へ進む
